# 15 — REALA ACE 右列（+R/+Ye/+G）移除补丁：4 字节数据改动

> 目标：`FWUP0024.DAT`（X-T4 二改，v2.12 派生）
> 结论来源：`13-fsim-ui-code.md`（team 反汇编/数据追踪）+ lead 独立复算验证
> 产出固件：`out/patch_no_reala_rightcol.DAT`
> **状态：【已实测生效】2026-11-09 上机确认：右列消失，REALA ACE 出图仍为彩色。** 此改法可作为标准流程复用。

---

## 0. 一步到位速查（下次照这个做）

1. **定位右列**：设备/固件里"某胶片模拟槽位有 +R/+Ye/+G 子选项" ⇒ 查 SETP 1070 的 12 项表（sec0 `0x4F40C0`），找 `{u32 值, u32 子SETP指针}` 中第二字段非 0 的那条（黑白类 = value 7 / ACROS = value 18）。
2. **改指针前先溯源**：`tools/fflz_trace.py <out_off>` 看目标 4 字节是 **literal**（可直接改压缩流）还是 **copy**（回溯引用，须改源头，否则会污染共享字节的其它表）。
3. **改两处**（still 表 + movie 表）：DAT `0x4BB45C..0x4BB45F` → `FF FF FF FF`；DAT `0x4BB606` → `FF`。
4. **重算主校验和**：`ck = 0xFFFFFFFF - sum(logical[0x274:0x274+0x2FC0020])` → 写文件 `0x20C`；`logical = 明文头[0:0x274] + (file[0x274:] ^ 0xFF)`。
5. **自检**：`tools/patch_no_reala_rightcol.py` 会验证——DAT 只变 7 字节、解压 sec0 恰好变 8 字节、sec1/2/3 sha 不变、R0..R5 全 OK。
6. 一般规律：**这类"子选项/父子设置"都是 SETP 值表里的第二字段指针**；清指针 = 去掉子面板，不用重压缩固件。


---

## 1. 右列到底是什么【确证】

胶片模拟选择界面是**两层 SETP**：

```
SETP 1070 (UI_SETP_FILM_SIM) 记录 @sec0 0x4F4920 (VA 0x01515920)
  └─ p2 值表 @sec0 0x4F40C0 (VA 0x015150C0)：12 条 × 8B {u32 值; u32 子SETP指针}
       [0]=0  [1]=3  [2]=1  [3]=14  [4]=13  [5]=12  [6]=15  [7]=16  [8]=17
       [9]=18 → 0x01514FA0 = SETP 1071 (ACROS 子记录)
       [10]=7 → 0x015155E8 = SETP 1072 (黑白子记录)   ← REALA ACE 现在占的就是这一格
       [11]=5  [12]=0x7FFFFFFE 终止
```

* **只有 value=18（ACROS）和 value=7（黑白）两条带子记录**，其余 10 条指针为 0 —— 这正好对应"只有黑白类会展开右列"。
* 子记录 1072 的值表 @sec0 `0x4F4398`：`8, 10, 9, 11`（依次为 NON / +Ye / +R / +G），这就是右列的 4 个选项。
* 该表在官方 v2.12 与二改中**逐字节相同** ⇒ 二改只是把 value=7 那一格的文字/图标换成了 REALA ACE，家族指针没清，于是继承了右列。

## 2. 补丁（原地改，无需重压缩）

改的是 **compressed stream 里恰好是字面量 run 的字节**（用 `tools/fflz_trace.py` 逐字节溯源确认）：

| 文件偏移 | 改前（raw） | 改后（raw） | 作用 |
|---|---|---|---|
| `0x4BB45C..0x4BB45F` | `17 AA AE FE` | `FF FF FF FF` | 清掉 still 表 value=7 的指针高 3 字节 + 低字节（逻辑值 `E8 55 51 01`→0） |
| `0x4BB606` | `37` | `FF` | 清掉 movie 表 value=7 指针的低字节（`C8`→`00`） |
| `0x20C..0x20D` | `C6 65 BA 56` | 重算 | 主校验和 → `0x56BA681D` |

> 说明：movie 表的指针低字节是独立字面量 `0xC8`，其余 3 字节是 FFLZ 从 still 指针处**复制**的；所以必须两处一起清，否则 movie 表会留下非法指针 `0x000000C8`。

## 3. 验证结果（`tools/patch_no_reala_rightcol.py` 自动跑）

```

解压 4 段尺寸: 7,421,952 / 9,437,184 / 10,240,000 / 6,446,369（全部不变）
sec0 解压后差异: 恰好 8 字节 → 0x4F4114..0x4F4117 与 0x4F465C..0x4F465F
sec1/sec2/sec3: 逐字节相同（sha256 一致）
still 表 value=7 : value=7  ptr=0x00000000 ✓
movie 表 value=7 : value=7  ptr=0x00000000 ✓
主校验和: 0x56BA681D 自校验 OK；R0..R5 六个分区校验全 OK
```

## 4. 预期效果

* 胶片模拟 → REALA ACE：**不再展开 +R/+Ye/+G 右列**（值 7 那一格不再有子设置项）；
* 电影模式里同位置的那一格也一并生效（同一补丁）；
* ACROS 不受影响（它的指针在另一条，未动）；RAW 开发菜单（SETP 1655）不受影响。

## 5. 风险（刷后必须确认）

1. **出图颜色**：如果 UI 在没有子记录时提交"左列值 7"，而 REALA ACE 的渲染参数其实挂在"子值 8（NON）"上，则 REALA ACE 可能变黑白。
   * 若变黑白 ⇒ 说明渲染挂在 8 上，下一步补丁应改成"保留子记录但只留 NON 一个选项 / 或让 UI 默认提交 8"，需要另做（子值表字节不是字面量，不能原地改，可能要重压缩 sec0 或改父表值）。
2. ACROS 仍有右列（正常，它是真黑白）。
3. 其余字节零改动，回退直接刷回 `FWUP0024.DAT`。

## 7. 后续：Q 菜单与「STD」残留（第二轮，未交付）

上机后仍有两个现象：
1. **选胶片模拟界面右列**残留一个只读的 `STD` 状态（子列表已进不去）。
2. **Q 菜单**滚波轮仍能切到黑白的 3 个滤镜（+Ye/+R/+G）。

### 7.1 根本原因（已定位数据）

固件里胶片模拟有**两套呈现**：
* **两列呈现**：`SETP 1070` 12 项表（sec0 `0x4F40C0`，条目带子记录指针）← 第一轮补丁改的就是这里；
* **平坦呈现**：18 项值表 `0,3,1,14,13,12,15,16,17,19,21,20,22,8,10,9,11,5`，共 **5 份副本**：
  `0x4E2D60`（记录 `0x4E35D0`, tag(3,1), id=1070）、`0x4E3188`（记录 `0x4E35B0`, id=1073）、
  `0x4F3078`（id=1078 SELECT_1）、`0x4F34C0`（id=1079 SELECT_2）、`0x4F3908`（id=1080 SELECT_3）。
  Q 菜单/快捷项用的是这一套 ⇒ 所以还能滚出 `+Ye/+R/+G`（值 10/9/11，以及 8=NON）。
* 另有一套**重复银行**（`0x4CA970` / `0x4CAEB8`，对应记录 `0x4CA930..0x4CB1B0`），结构与 bank A 相同。

### 7.2 为什么不能像第一轮那样 4 字节解决（实测）

用 `tools/fflz_trace.py` 逐字节溯源后发现：这些平坦表/指针的字节在 FFLZ 压缩流里**大量是回溯引用或与他表共享同一输出字节**。尝试过的两版补丁都在「解压后对比」阶段发现**连累兄弟指针**：

* 清 **bank B** 1070 的 value=7 指针 → bank B 1073 记录（`0x4CB190/0x4CB1B0`）的 `p2` 被连带改成非法值 `0x000000B8`；
* 改 **1079** 的 p2（想指向 12 项表）→ `1076` 的 SELECT 映射表（`0x4F3FC0`）条目被连带改坏；
* 改 **flat1070** 的 p2 → 其 `p3`（消息表指针）被连带改坏；改 **1080** p2 同样连累 `p3`。

⇒ **数据级原地补丁在这几张平坦表上不安全**，v3/v4 固件已在验证阶段拒绝交付（`out/patch_v3_no_bw_filters.DAT`、`out/patch_v4_test_select2.DAT` 仅供追溯，**不要刷**）。

### 7.3 可行的下一步（重压缩路线）

sec0 在文件里的空间预算：`0x5C0274 - (0x260274+20) = 3,538,924 B`，当前 packed=`3,450,526` ⇒ 有 **≈88 KB 余量**。
所以可以做「**重压缩 sec0**」：用自己的 FFLZ 编码器重新打包（不改其它段/容器偏移，只改 sec0 头里的 packed/pages 与文件内那段数据），
然后就能**自由重写**平坦表（删掉 8/10/9/11 或重排），甚至处理「STD」残留。

安全流程（建议）：
1. **S1：等价重压缩验证**——把 sec0 解压后按相同内容重新压缩，生成固件（内容零变化），刷机确认一切正常（这一步证明编码器/头字段/余量处理没问题）；
2. **S2：在 S1 基础上改平坦表**——去掉 BW 变体（值 8/10/9/11），必要时调整 `STD` 显示；
3. 每步都保留 `FWUP0024.DAT` 回退。
