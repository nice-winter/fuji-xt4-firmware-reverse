## 1. JPEG 比例/尺寸：为什么不是"改一个枚举"

原始需求：在机内"图像尺寸"菜单里新增比例（4:3 / 5:4 / 65:24），且**实时取景必须同步裁切**。用户明确拒绝
"取景仍 3:2、只裁最终 JPEG"的方案（记录在 `xt4-codex/analysis/jpeg_aspect_followup_20261107/SIMPLER_DESIGN.md`）。

### 1.1 菜单与存储（静态链已闭合）【确证】

- 24 条 × 20 B 的记录表在 image5 `0x15629d8`：`+0` combined id、`+4` size、`+5` aspect、`+8/+12` 显示宽高、
  `+16` enabled、`+17` UI 序号。
- 正向路径在 image6：`0x2053730` 按 combined id 查表 → `0x20576cc` 用 `+4` 调 `0x1128024` 写 active size、
  用 `+5` 调 `0x112857c` 写 active aspect → `0x115fd4c/0x115fed0` 持久化。
- 持久化落到 `0x1aca4a4 + bank*0x9a0c + 0x2ca`，selector 是 **`0x413`**（照片）。
- 屏幕侧是**另一张**表：12 项 value/display 表（含 3 项 crop）在 `0x152b048/0x152b0b0`，扩容要重定位两表并
  更新两个 descriptor 的 4 个指针——**隐藏槽 enabled≠屏幕菜单已实现**。

证据：`xt4-codex/analysis/jpeg_aspect_20261106/menu_storage_findings.md`（含原码窗口与 REA 绑定）。
原始 24 项表里已有**禁用**的 L 4:3 / L 65:24 / L 5:4（combined id 0/4/5，尺寸占位 3120×2080），
这是"新增"而不是"替换"的入口。

### 1.2 原生预缩放与真实中心裁切【确证】

- 普通照片非方形比例会**先按 `(size, 3:2)` 预缩放**（`0x21a481c`，由 `0x21a5214` 调用）。所以新比例必须保持
  `size=L`；直接改 M/S 的输出尺寸会先被缩小再裁切。
- 真实像素裁切块是 `0x21a6518..0x21a65a0`：改 YC 地址、`widthBytes=2*w`、`height=h`、extent=`h*stride`，
  **保留 stride**。这是真·缓冲区裁切，不是改标签或只写 EXIF。

### 1.3 编码器：白名单 + profile 缓存【确证】

- 尺寸→profile 分类器 `0x401b468` 在 `0x401c490` 的 6 字节条目（最多 44 条）里精确匹配 `(width,height,role)`，
  `width==0` 提前退出。原始主图 L 条目只有 `(6240,4160,1,5)`、`(6240,3512,1,8)`、`(4160,4160,1,11)`。
- 新尺寸查不到 → 返回 profile 0 → 调用者 `0x401b858` 在 `0x401b89c` 判零后进入 `0x401b8ac` **死循环**。
- `0x401b4e4` 还按**面积**缓存 profile 目标值 `w*h*rate/80`；把多个新尺寸映射到同一 profile 会让结果
  取决于"先选哪个尺寸"。**只绕零检查是不安全的。**
- 编码输入源地址必须 **16 字节对齐**：`5544×4160` 的中心偏移 696（8 mod 16）会在 `0x20d2a74` 处卡死——
  这条把"数学上精确的 4:3 最大尺寸"直接排除了。

### 1.4 EXIF / RAW 元数据 / 内嵌图【确证】

- EXIF 尺寸：`0x22108a4`（CreateExifHead）先填 context `+0x31e4/+0x31e0`，经 `0x21ac144` 到 `0x22217d8`
  写 metadata `+0x2a0/+0x2a4`；image5 tag 表 `0x1571428/0x1571448` 就是标准 A002/A003，
  **不需要伪造标签**。注意 `+0x3114` 置位的类型会改走 `(size=0x23, aspect=1)` 固定宽高——RAW 相关分支另有尺寸，
  不能全局覆盖。
- 内嵌 YC：`0x2201b18` 只把 aspect 1/2/3/7 当特例，**aspect 4/5 一律落到 4:3**；实测 helper 上
  aspect4/5 输出的还是 640×480。thumbnail 另走固定 160×120 参数。
- 用户实机事实：**只拍 RAW 时"图像尺寸"选项本来就无效**，这是原机行为，不是补丁缺陷。

证据：`xt4-codex/analysis/jpeg_aspect_20261106/ENCODER_FINDINGS.md`、`jpeg_pipeline_findings.md`、`RAW_METADATA_FINDINGS.md`。

### 1.5 第一轮候选与硬件否决【实机验证】

- `dfba5b47`（离线 592 组 getter / 7 组 profile / 七校验全过）实机只**部分**成立：
  4:3 的 JPEG 保存与回放正确；实时取景仍 3:2；5:4 / 65:24 **对焦点消失**、按一次快门后画面继续刷新但操作锁死、
  写卡灯持续红绿闪；三种新比例对焦都黑白闪。
- 复现到的具体缺陷（【确证】）：5:4 的检测图像补边用 `(W*3/4 - H) >> 1`，5200/4160 得到 **2147483518**
  而不是合理边距（无符号下溢），回绕后描述高度变 3900、地址也错。**但 65:24 不触发同一减法**，不能套用。
- donor 对照（GFX100S `GXUP0004.DAT`）解释了这个缺口的来源：donor 的 `0x22973fc` 把 **1:1 / 5:4 / 7:6 一起**
  送横向补边，X-T4 只让 1:1 走横向。donor 尺寸 getter 显式支持 aspect 0..6，X-T4 只有 5 列。
  但两机 YC 描述字段布局不同（donor `+0x1c/+0x20/+0x24` vs X-T4 `+0xc/+0x10/+0x14`），**不能直接 copy**。

于是有 `IMPLEMENTATION_STOP.md` 的停止决定：四条理由——显示/AF 的 `FRAME_ASPECT` 枚举定义两机不兼容
（X-T4 `0=3:2,1=16:9,2=17:9,3=1:1`；donor `0=4:3,1=3:2,2=16:9,3=17:9,4=1:1,5=5:4,6=7:6,7=65:24`）、
65:24 保存失败没有闭环解释、内嵌图是多级任务（`0x21a7b48→0x21a7978/0x21c8a5c`，中间 buffer 尺寸≠送 JPEG 尺寸）、
跨机工作区结构不兼容。`SIMPLER_DESIGN.md` 改为"更窄架构"：保持原生 3:2 生产端、把输出裁切选择**快照**到照片任务、
显示端用原生 crop 接口 + AF 坐标换算、JPEG 端在原生 L 像素后做中心裁切。**这是设计方向，未实现。**

### 1.6 后续路线：原生 1:1 共用路径 → 黑屏 → 可用

| 包 | 关键改动 | 实机结果 |
|---|---|---|
| `4f354c70` | 把三比例挂到原生 1:1 共用路径（含显示/FDI/reservation） | **开机全黑**，撤回 |
| `1012db4c` | 修 XN 尾区：helper 移进已证明可执行的 padding，尾区只留 FDI 数据 | 三个新比例 JPEG 正常；取景仍 3:2、主摘要空、Q 仍 M、5:4/65:24 张数 0 |
| `2ceee71d` | 只 hook 已确认的 3 个 image6 显示调用点（局部 wrapper + 6 字节 count），公共函数字节全还原 | 取景与三个新比例 JPEG **已被用户确认正常** |
| `7be75eca` | 图标资源解析 / 菜单 Q 图标 / 尺寸元数据 / OSD 张数 selector | 主菜单与 Q 菜单显示**已被用户确认** |
| `50f6d54e` | Q 菜单原生样式 + 拍摄状态 M→L 数据引用 | 用户反馈"基本正常"；但新比例下 AFC 追踪框向右下偏移 |

### 1.7 本节的证据等级 / 现状 / 下一步

- 证据等级：菜单/裁切/编码/EXIF 链【确证】（原码 + REA 字节绑定 + 受控原生执行）；JPEG 输出与取景
  【实机验证】（`2ceee71d`/`1012db4c`）。
- 现状：**JPEG 三个新比例已可用**；UI 细节（张数为保守 alias、部分图标字形偏小）与 RAW+JPEG 完整区域仍属"未逐项验证"。
- 下一步：不要重开"再加一张尺寸表"的老路。若继续，需要（a）RAW+JPEG 有效区域/裁切元数据专项实机核对，
  （b）特殊照片模式（连拍/包围/HDR/全景）逐项确认，（c）机内 RAW 显影的新比例映射（当前仍未实现）。

## 2. AF 与追踪：从"框位置"到"网格下溢"

### 2.1 症状演化【实机验证】

1. 新比例（尤其 4:3）下 **AFC 追踪框整体向右下偏移**、框变小（`50f6d54e` 时代）。
2. 局部修 UI 区域中心 fit 的 `1fb55839` **实机失败**。
3. 改"矩形显示目的坐标"的 `76daac32` 也**实机失败**。
4. 改"矩形源区域"的 `a7f896c5` 后，**用户确认 AFC 已正常**；但 4:3 **AF-S 单点**仍有严重实时增亮 + 不合焦
   （中心与边缘都有，排除"只在可达边界"）。
5. 之后 `d014099a`（搜索轴裁切分类器）与 `a01e9785`（局部统计副本 3:4→6:8）**连续实机失败**。
6. `dfc98269`（4:3 原生网格表 13→11 列）后，用户反馈"功能总体正常"，仅剩新比例 + 即时检视/竖拍的问题。

### 2.2 为什么"改一个坐标"不够【强】

- `a7f896c5` 的根因（【确证】）：原生 `0x2352cf0` 先按 3:2 建有效区再按比例裁；`0x2352f3c` 产出的
  4:3/5:4 框已在该区域内，而 `76daac32` 读取端却沿用 640×480 / 600×480 的旧源区域，同一个框被压到约 **88.75%**。
  候选把 4:3 源区域取 `[36,27,568,426]`、5:4 取 `[54,27,532,426]`（居中计算），再走原生 `0x216ab18` 映射。
- 但"显示框对"≠"算法可达范围对"。`0x2456898` 的原生 reach bounds 每个矩形都以 (319.5,239.5) 为中心，
  3:2=`(0,27)..(639,452)`、1:1=`(107,27)..(532,452)`、5:4=`(54,27)..(585,452)`、65:24=`(0,122)..(639,357)`；
  新 4:3 却返回整个 `(0,0)..(639,479)` 画布。**说明 4:3 走的是另一条几何路径，不是简单的居中差。**
- 另有一条独立的实时坐标重映射 `0x21d6c88`（旧/新几何混用），但**逆运算执行**显示：对检测中心与四个边界点，
  新旧比例的中心映射误差为 0（72 组对照）。**所以"缺新 aspect 分支"本身不构成缺陷**，不能凭"少个分支"就打补丁。

### 2.3 43 网格（4:3 grid）与 `grid2468` / stats alias

- 具体缺陷【确证】：网格表 `0x13d9390` 的条目是 `(3,4,9,13)`（宽 9、高 13）。`0x1333bb0` 的
  `mls r3,r4,r1,r8` 计算 `2773 - 218*13 = -61` → **`0xffffffc3`**，再右移 1 并加 fit 原点 173 → `0x8000008e`。
  这是无符号下溢，直接污染 `0x23522dc` 输出与最终网格原点。
- 只读内存实验把 `0x13d939c` 的 13 改成 11（与原生 5:4 的 9×11 一致）后，72 组用例里 3:4 的中心网格
  变成 `[27,216,373,15]`，与原生 5:4 的 `[27,216,374,15]` 只差 1 px。180 组点展开验证四角可用。
  **这条"只改一个表格字节"的修法就是后来 `dfc98269` 的内核。**
- `grid2468` / "stats alias" 是更早的两条弯路：把 3:4 当作"等价 6:8"去改共享几何/统计入口。它们被明确拒绝
  （`STATS_ALIAS_INDEPENDENT_AUDIT.md`、`CLASSIFIER_CANDIDATE_INDEPENDENT_AUDIT.md`），理由同样是被
  `0x229c3c4` 之后的归一化/裁剪链抵消，改共享函数等于给所有比例引入未验证几何。
- 顺序教训：`d014099a`（搜索轴 61 字节）→ 失败；`a01e9785`（+36 B helper 改 stats 副本）→ 失败。
  两次失败都不是"补丁没生效"，而是**改了不承担该症状的那一段**。`dfc98269` 明确不累加这两次改动。

### 2.4 搜索增亮（search gain）【强 / 部分未定位】

- 用户观察：AF-S 搜索时实时画面明显增亮，但**JPEG 曝光本身没有观察到异常**。这不等于传感器增益或
  AF 状态已被测量。
- 已闭合的真实增益链：`0x23f0c44` → EV→百分比 `0x22a09c8` → `0x243a580`（消息 1603）→ `0x2429da8`
  写 snapshot `+a0` → `0x228d720` 把三路 RGB 增益乘以 `percent+a0/100` → `0x20994c8` 写入 ISP context `+a6/+a8/+aa`。
- **没有找到比例相关的准入条件**：这份 gate（`0x233b9e0`→`0x23b0bf0`，写 RAM `0x2931321`）里没有 ratio 输入；
  GFX donor 的同名函数控制流完全相同。并且这些窗口与已修曝光的 `618a3edd` 基线**逐字节一致**——
  说明候选包并没有直接改增益代码。
- 因此当前更可能的解释是：AF 拿到不匹配/空的目标区域，**停留在搜索状态更久**，正常预览增亮行为被延长。
  这是【推测】，不是结论。禁止用"抑制搜索增益"或"照搬 donor 常数"来压制几何错误造成的闪烁。

### 2.5 本节证据等级 / 现状 / 下一步

- 证据等级：网格下溢【确证】；AFC 框修正与 4:3 AF-S 缓解【实机验证】（用户口径"总体正常"，**未逐项验证**）。
- 现状：**AF 不是"已完美"**。可靠口径是：`a7f896c5` 起 AFC 可用；`dfc98269` 起 4:3 AF-S 的网格坐标不再溢出，
  用户主观反馈"总体正常"；搜索增亮没有独立测量证据，也没有被单独验证消失。
- 下一步：`xt4-codex/analysis/jpeg_af_tracking_20261108/afs_followup/CURRENT_STATUS.md` 明确要求
  **不要重开 AF/曝光**、不要把失败的方向/统计候选叠进下一个包。若继续，需要（a）真实 AF 统计数据缓冲区
  （ring `3678e30+row*120` 的 `+9b18..+9b3c`）的生产者绑定，（b）timed review 与 AF 的 mode 状态区分，
  （c）4:3 AF-S 合焦质量的**可重复实机判据**（不只是"看起来正常"）。

## 3. 即时检视 / 竖拍检视

### 3.1 症状与设置模型（先纠正两处误读）【实机验证】

- 用户修正后的现象：**所有**新比例（4:3/5:4/65:24）、**横竖拍都有**，只有把即时检视设成 **0.5 s / 1.5 s（timed）**
  才出现画面损坏；检视 OFF、连续检视、以及事后 PLAY 同一张已存 JPEG 都正常；检视结束后实时画面恢复；
  已保存照片像素正常。
- 另一个独立现象：**连续检视下 4:3 被显示成 3:2**，而 5:4 / 65:24 比例正确。这两件事必须分开追。
- 设置枚举的坑：UI 名字表 `0x24ddd20` 里 `PREVIEW0/QUICK1/S2/L3/_4/OFF5` 只是**界面标签**，不是存储值。
  真正的转换是 `0x1022f7c→0x1121f5c`，指针 `0x1700694[A]=0x14d14a0`，每行 4 word
  `(stored,*,runtime_mode,timer)`：`0→0x9b/15`、`1→0x9b/5`、`2→0x9c/ffff`、`3→0x86/0`、`4→0x9b/fff1`、`5→0x9d/0`。
  原生名字：`0x9b=POSTVIEW`（timed）、`0x9c=PREVIEW`（continuous）、`0x9d=EXPANSION_PREVIEW`、`0x86=OFF`。
  → **raw 值 0/1 都是 timed，只是定时器不同**，这解释了用户的 0.5 s / 1.5 s 区分。

### 3.2 显示契约根因：行 stride 不匹配【确证】

这条是本主题里**最硬的一条离线结论**（`xt4-codex/analysis/jpeg_portrait_review_20261111/DISPLAY_CONTRACT_ROOT_CAUSE.md`）：

- 照片图像平面几何表是 `0x25cc51c`，每行 32 B；消费链 `0x21779dc → 0x21776d0`，最终经
  `0x2197fcc / 0x2198064 / 0x2198218` → `0x21980f0` 提交。
- 临时帧缓冲池 buffer28 是 3 个描述符（`0x25e0b5c`，由 `0x25d04dc` 选择）：容量 2764800 B、**pitch 2880 B**、高 960。
  common worker 写进去的原生画面是 LCD 900×600 / EVF 1280×960，**pitch 保持 1440 px（=2880 B）**。
- 新 JPEG 比例复用的是 legacy aspect 0/4/5 的行，而这些行描述的是别的原生格式：

  | 平面行 | 旧布局 | 实际临时载体 |
  |---|---|---|
  | LCD0 | pitch 1024 px、高 768、baseY=-43 | pitch 1440 px、900×600 |
  | LCD4/5 | pitch 1600 px、高 768 | pitch 1440 px、900×600 |
  | EVF7 | pitch 1024 px、高 768、baseY=-43 | pitch 1440 px、1280×960 |
  | EVF11/12 | pitch 1600 px、高 1200 | pitch 1440 px、1280×960 |

  原始 3:2/16:9/1:1 行用的都是 1440 px pitch。**新比例带着不匹配的行 stride 进入照片平面**——这不再是
  "合成 worker 下溢"那种假设，而是生产者池 + 渲染表 + 提交算术三方一致的契约错误。

### 3.3 离线候选 `29377c8d`（**未实机**）

- 改动：image6 六行 32 B 表改成真实载体尺寸 + 中心 ROI（LCD 4:3=800×600、5:4=748×600、宽=900×332；
  EVF 4:3=1280×960、5:4=1200×960、宽=1280×472）；image5 两个数据 word 补 LCD 4:3 缺失的 50/50 边界。
  **不改任何可执行字节、ABI、图像平面状态或全局 crop 函数。**
- 离线验证：56 组原/候选 `0x21779dc / 0x2178088 → 0x21776d0` 成对比较、108 组 common worker/FDI/驱动用例、
  324 组 buffer28 pitch/范围验证；原 L、另一平面、EVF inset 格式输出不变。
- 限制：相机状态、aspect/display/format、源帧都是显式夹具；MMIO/DMA 是捕获边界；**没有模拟扫描输出与真实 0.5/1.5 s 时序**。
  → 只能是"未实测候选"，不是修复。

### 3.4 仍未闭合的部分

- **timed `0x9b` 的生产者身份**未定：`0x21cf0bc` 的 row 8 把消息 `0x116a` 交给 phase handler `0x21d1ae0` → `0x21e0f48`，
  该函数从模板 `0x367d4f0` 拷帧状态、按全局 `0x3678e74/75` 填 aspect 几何，再经 `0x2204394` 发 `0x1242`。
  但没有任何静态证据把 **发送者** 绑到 runtime mode `0x9b`。已知 `0x116a` 构造器 `0x21cc8c8` 的
  两个直接调用者 `0x216b33c/0x2178520` 都是显示/相机状态更新，且从 `0x9b` 定时器回调到它的直接调用图里没有路径
  （不排除间接/表驱动）。
- **worker `0x22027ac` 的无符号下溢**只能当**负对照**：`(canvasH - scaledH) & ~1` 在 4:3（算得 675）/5:4（720）
  JPEG 尺寸输入下会得到近 4 GiB 填充长度；但它的已观测生产者 `0x21e18c0` 明确写 runtime mode **`0x9c`（PREVIEW）**，
  属连续预览路径，且不能解释 65:24。**不能据此打补丁。**
- `0x21fd464` 的一处旧描述需纠正：它改的是描述符 **`+4`（指针）**，不是 stride；`0x2209c58` 正常分支会把
  128 的 stride/宽/高/格式复制到 41c 并重算长度，因此"41c 是被旋转的不同 stride 平面"这一说法不成立。
  六个比例的原生 crop+translate 探针里，所有源范围都落在 41c 载体内部且 16 字节对齐——**负向检查**。
- 竖拍旋转：`0x1fa9550` 的 sysdisp 选择器在 9b/9c 配置下输出命令相同（32 对比较），`+b23` 是显示 commit 的
  scan/flip 模式，**不是 JPEG 软件 90° 旋转**；全局压掉命令 165 属"用装饰性办法掩盖"，禁止。

### 3.5 本节证据等级 / 现状 / 下一步

- 证据等级：显示契约错【确证】（原码链 + 324/56/108 组原生执行）；timed 根因【未定位】（发送者未绑定）；
  worker 下溢【强】（算术已复现，但输入未观测）。
- 现状：`29377c8d` 是**离线通过、未实机**的候选；连续 4:3 的 aspect 显示错误另有其因，尚未修。
- 下一步（按 codex 记录的顺序）：先绑 `0x116a` 生产者 → 判定其相机状态是 `0x9b` 还是 `0x9c`；再取 timed 路径真实的
  源描述符（ptr/stride/width-bytes/height）与 `0x9c`/OFF/原生 1:1 对照。**在有具体补丁点和可判定的离线回归之前，
  不要为了"试一下"而改全局方向、aspect 缓存、定时器或 crop hook。**

## 4. 启动失败：两次黑屏与它们教给我们的东西

### 4.1 `4f354c70`：把代码放进了禁止取指的区域【确证】

- 原启动代码 `0x1291690..0x12916a4` 对区间 **[0x16ae000, 0x1735000)** 设置 flags=3，原页表生成器把 flags3 编码成
  **XN（禁止执行）**。`4f354c70` 把三个新 helper 放进该区间，并从公共入口 `0x2194b40` **无条件**跳过去。
- 在真实权限模型下执行旧 L 查询：稳定基底能正常返回；`4f` 在新入口触发 **FETCH_PROT**。这就是确定的启动阻断缺陷。
  （没有整机启动轨迹，所以只能说"缺陷确证"，不能说"唯一物理原因已证明"。）
- 修法：把指令搬进**已证明可执行的 padding**，尾区只留 FDI 数据；同时保留原 query mode/指针守卫与分类器部分指针行为。
  中间产物 `30bd4706` 被独立离线审计拒绝（分类器多读一个 halfword，与原固件不符），**未交付**；
  `1012db4c` 通过独立审计 + 88 个 REA 源字节窗口后成为"能开机且能出三新比例"的基底。

### 4.2 `d4f7f93d`：早启动阶段依赖了尚未加载的模块【强】

- 原 image5 startup 的 catch-all 在 `0x12916f0..0x1291700` 对 `0x1e0f000..0x40000000` 设 RW+XN(flags3)；
  **image6 只有在后续 setup 之后才变成可执行**。
- `d4` 把公共函数 `0x12eeaac` 改成无条件跳到 image6 的 `0x1e0f95c`。在"pre-ID6"权限状态下：
  `1012` 的原 3:2 查询正常返回，`d4` 的首次取指就 **FETCH_PROT**；一旦 image6 可执行，两者都正常。
  → 这是"在原生映射状态下新增的早启动依赖"的复现，**不等于**拿到了整机启动现场的调用栈。
- 旧 fixture 之所以没抓到：它**预先映射了全部模块**，从结构上不可能发现"模块还没加载"这一类问题。
  另外白名单只约束"是否修改尺寸"，**不约束"是否执行新代码"**——所有原比例调用也会先跳进 image6 veneer。
- 同期的只读 ABI 审计（9 个对齐 BL 调用点 / 45 组样本）**没有**发现能解释黑屏的 volatile/callee-saved/SP 缺陷。
  **"ABI 干净"与"能开机"是两件事。**

### 4.3 之后的正确姿势

`d4` 之后的新方案一律：**只 hook 已确认的 image6 显示调用点，公共 helper 字节完全还原**
（`2ceee71d` 就是这样：3 个显示点 + 14 个操作，公共 `0x12eeaac/0x13342c8` 与启动代码原样），
并且先做"只开关机 → 旧比例 → 新比例"的分阶段实机步骤。

### 4.4 本节证据等级 / 现状 / 下一步

- 证据等级：XN 取指缺陷【确证】（页表 flags 编码 + 权限感知执行复现）；早启动依赖【强】（可复现，缺整机 trace）。
- 现状：`4f354c70`、`d4f7f93d` 均为**实机失败**，DAT 保留仅供追溯，不再推荐；
  `1012db4c` 是"最后被实机证明能开机并出图"的包。
- 下一步：任何新包都必须过三关——（a）指令只落在已证明可执行的区域；（b）启动期调用图里不新增跨模块依赖；
  （c）独立解包 + 七校验 + 回读 SHA + REA 字节窗口。**"本地能跑"不是"相机能启动"。**

## 5. 跨主题的风险与待澄清点

1. **状态文件比 README 新**：同一个包里 README 写"未实机"，而同目录的 `实机通过.md` / `REJECTED_CAMERA_FAILURE`
   才是终态。本文与 [24](24-hw-candidate-status.md) 一律以后者为准。
2. **用户反馈被修正过两次**（先"仅竖拍"，再"横竖都坏"，且"仅 timed"）。写结论时要带"截至 2026-11-11 用户口径"。
3. **AFC 可用 ≠ AF-S 可用**；AF-S 缓解 ≠ 已逐项验证。不要把"用户说总体正常"升级成"AF 已完美"。
4. **显示契约错**是当前最有价值的可验证根因（有具体表行、具体 pitch 数字），但它解释的是"timed review 损坏"的一部分，
   不解释连续 4:3 的 aspect 显示错误。
5. **不要用装饰性手段过症状**：关 AF/人脸、压增益、伪造预览/EXIF、只裁 JPEG 不管取景、允许写卡卡死却称成功——
   这些在 `SIMPLER_DESIGN.md` 里被逐条列为"不采用"。
