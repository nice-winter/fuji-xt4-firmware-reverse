## 0. 结论摘要（先看这里）

1. `[确证]` 文件 = **明文容器头 + 逐字节取反(XOR 0xFF)的固件载荷**。取反载荷的物理起点是 **0x274**（不是 0x378）。
   三条独立证据：① 6 个 region 偏移链末端 `0x30CEF54+0x18000=0x30E6F54` 恰等于 `filesize-0x274`；
   ② `@0x20C` 校验和 = `0xFFFFFFFF - Σ(payload[0:0x2FC0020])`，只有 base=0x274 时逐字节命中；
   ③ 载荷内 section 数据起点全部 = `0x274 + 0x20000*k`。
2. `[确证]` 头部字段：`os_type=6 @0x000`、model code 区 512B @0x004、`version1=2 @0x204`、`version2=0x12 @0x208`（→ v2.12）、
   `checksum @0x20C`。
3. `[确证]` 校验和算法 = **8 位字节和的补码**：`cksum = 0xFFFFFFFF - (Σbytes mod 2^32)`。
   主校验 `@0x20C` 覆盖 **main body = payload[0x000000, 0x2FC0020)**；
   另有 6 个 region 的 `(checksum, offset, size)` 描述，**7 段恰好无缝覆盖整个 payload**（主体验算 7/7 通过）。
4. `[确证]` 头部 `u32@0x000 = 6` 不是 512B 文本表的条目数（该表非空槽位=11），而是**二进制描述表中的 6 个 region 数**（6 条描述逐条校验通过）。
5. `[未定]` 0x004..0x203 的 512B model code 区内容为「ASCII-hex 的 ASCII-hex」文本，两次 hex 解码得 32 槽 × u32 BE，11 个非空槽
   （`0x00056001,0x00056002,0x00056004,0x00056009,0x00057001..0x00057008`），语义未定（见 §3）。
6. `[未定]` **0x274 vs 0x378 冲突**：物理/校验证据指向 header=0x274；公开资料（fujihack）称 type-6 扩展头明文到 0x378。
   两者重叠区 0x274..0x378 的归属是本报告唯一的结构性未决点（见 §8）。
7. `[确证]` **无整体签名/footer**：尾部 75,814 字节全 0；无 MD5/SHA footer；全文无可识别 RSA/ECDSA/X.509/CMAC 签名块。
   完整性只靠弱校验和（8-bit 求和取反）。

## 3. 0x004..0x203：512 字节 model code 区（双重 ASCII-hex）

### 观测
- 512 字节全部是字符 `'0'..'9'`（0x30..0x39），无 a-f、无分隔符。
- 第 1 次 hex 解码 → **256 字节**，仍全部是 `'0'..'9'`（ASCII 数字文本）。
- 第 2 次 hex 解码 → **128 字节 = 32 × u32 BE**。
- 32 槽中 **11 个非空**，其余 21 槽全 0。

### 逐条 dump（内层 128B → 32 × u32 BE，`slot: value`）
```
slot00: 0x00056001   slot01: 0x00056002   slot02: 0x00056004   slot03: 0x00056009
slot04: 0x00057001   slot05: 0x00057002   slot06: 0x00057004   slot07: 0x00057005
slot08: 0x00057006   slot09: 0x00057007   slot10: 0x00057008   slot11..31: 0x00000000
```
相邻非空值之差：`+1, +2, +5, +4088, +1, +2, +1, +1, +1, +1`。
即两组：`0x00056001/2/4/9` 与 `0x00057001..0x00057008`（0x56000 与 0x57000 相差 0x1000）。

### 已排除 / 并存读法
| 读法 | 结果 | 判断 |
|---|---|---|
| u32 **BE**（本表） | `0x00056001...`，32 槽 11 非空，槽位对齐干净 | 最可能（结构最整齐） |
| u32 **LE** | `0x01600500, 0x02600500, 0x04600500, ...` | 规律性弱于 BE |
| u16 **BE** 对 | `(0x0005,0x6001) (0x0005,0x6002) (0x0005,0x6004) (0x0005,0x6009) (0x0005,0x7001)...` | 与 u32 BE 等价拆分（高半 0x0005 恒定） |
| 十进制文本（每 8 字符） | `56001, 56002, 56004, 56009, 57001..57008` | 与 BE 读法同形（ASCII 全数字导致两解同构），无法排除 |
| 条目数 = `u32@0x000`(=6) | 11 ≠ 6 | **否**（0x000 是 region 数，见 §4） |

### 结论
- `[确证]` 该字段是「**hex 文本，且解码后仍是 hex 文本**」的双层编码（512=2×256=4×128 字节，边界精确）。
- `[强]` **公开工具的口径与本表一致**：EnglandLobster `fujitools/dat.py` 把 model-code 区描述为「digit characters at odd byte offsets, interleaved with 0x33」并按 **8 个 hex 字符一组**解释为
  「前 6 位 base + 后 2 位区域变体」——正是本报告的 `u32 BE` 读法（`0x000560|01`、`0x000560|02` …）；
  Trammell Hudson（2015, X100）同款字段、同样双解码，并猜测是「本文件包含哪些更新（which updates are present）的清单」。
  官方原版 X-T4 2.12 的该 512 字节与本文件**完全相同**（Lead/prior-art diff），说明它是官方固定字段，不是二次构建产物。
- `[未定]` 具体语义：11 个 `base=0x000560/0x000570 + variant` 码值的实际含义（更新组件清单？区域/SKU？机型变体？）尚无一手证据；
  可排除的是「条目数 = 0x000 的 6」（11≠6）与「文件偏移」（0x56001=352,257 等值在文件中无对应结构）。

## 4. 校验和算法（本任务的核心新确证）

### 算法
```
cksum(bytes) = (0xFFFFFFFF - (Σ bytes mod 2^32)) & 0xFFFFFFFF     # 8-bit one's complement sum
```
（等价于「字节和取反」；与 TCP/UDP 校验和同族，但只用低 32 位、无回卷折叠。）

### 验证结果（`tools/hdr.py` §5 可复算）

| 校验和字段 | 覆盖内容（payload 相对） | 覆盖模式 | 存储值 | 复算值 | 结果 |
|---|---|---|---|---|---|
| `@0x20C` | `payload[0x000000, 0x2FC0020)`（main body） | 逻辑(取反后) | `0x56B4BFF5` | `0x56B4BFF5` | **PASS** |
| `@0x210` | R0 `[0x02FC0020, +0xC000)` | 逻辑 | `0xFF6DB51F` | `0xFF6DB51F` | **PASS** |
| `@0x214` | R1 `[0x02FCC020, +0xD2CFC)` | 逻辑 | `0xF657A35A` | `0xF657A35A` | **PASS** |

  `0 → 0x2FC0020 → 0x2FCC020 → 0x309ED1C → 0x309EE8C → 0x309EF54 → 0x30CEF54 → 0x30E6F54(=EOF-0x274)`。
  → 这直接证明了 `u32@0x000=6` = **region 描述条数**，且 payload 基址 = **0x274**。
- `[强]` **R2/R3 异常**：这两条校验和只对「文件里保存的原始字节」命中，其余 5 条只对「取反后的逻辑字节」命中。
  可能解释：①R2/R3 两段在文件中**未取反**（混合存储）；②生成工具在取反前算的校验和；③这两段属于「头部元数据」而非固件正文。
  建议后续用官方原版对照这 0x238 字节的取反状态。
- `[确证]` 主校验 `@0x20C` 会随 payload 内容变化（本文件为二次构建，Lead 已证：官方同尺寸、头逐字节相同、仅 `0x20C` 与 3 个压缩流不同 → 0x20C 是「内容相关校验」，与算法一致）。

### 4.1 与公开资料/另一成员结论的核对（**解释掉“魔数 0x02FD03C5”**）

`03-prior-art.md` §3-1 记录：对本文件与官方原版都存在
`checksum = Σ(raw bytes 0x214..EOF) + 0x02FD03C5 (mod 2^32)`，但该常量来历未明。
本报告的分段模型可以**严格推导**出这个常量，说明它与 §4 的公式是同一个校验和的两种等价写法：

```
由本报告模型: 0x20C = 0xFFFFFFFF − Σ(logical payload[0:0x2FC0020])
其中 logical = raw^0xFF ⇒ Σ(logical) = 255·Lbody − Σ(raw body)，Lbody = 0x2FC0020
⇒ 0x20C = 0xFFFFFFFF − 255·Lbody + Σ(raw body)
而 Σ(raw[0x214:EOF]) = Σ(raw[0x214:0x274]) + Σ(raw body) + Σ(raw[0x2FC0294:EOF])
⇒ 0x20C = Σ(raw[0x214:EOF]) + K，
   K = 0xFFFFFFFF − 255·Lbody − Σ(raw[0x214:0x274]) − Σ(raw[0x2FC0294:EOF])
数值代入: 255·0x2FC0020 mod 2^32 = 0xF9041FE0，Σ(raw[0x214:0x274]) = 0x28D2，
          Σ(raw[0x2FC0294:EOF]) = 0x03FEB388
⇒ K = 0xFFFFFFFF − 0xF9041FE0 − 0x28D2 − 0x03FEB388 = 0x02FD03C5   （与实测常量逐位相同）
```
- `[确证]` 所以 `0x02FD03C5` **不是固定 seed/魔数**，而是「−255×主段长度 − 头部 0x214..0x274 字节和 − 尾部 0x2FC0294..EOF 字节和」的会计偏移。
- `[推论]` 它在官方/本文件两份样本中相同，是因为两次样本的 **0x214..0x274 头部字节、尾部 0x2FC0294..EOF 字节完全不变**（与 Lead 的 diff 结论一致）。
- `[结论]` 两套公式等价；**校验和被改写的段只有 main body 时，两种写法都成立**。若尾段（R0..R5）内容变化，`K` 会变，届时“老公式”需用本报告的分段公式重算。
- `[注意]` 公开 struct（fujihack）把 `0x210` 叫 `device_type/end`；本文件实测 `0x210 = 0xFF6DB51F` 且逐字节校验等于 `~Σ(R0)`。因为 R0..R5 是「版本级固定尾段」（官方/本文件相同），两种解释在现有样本上不可区分；本报告按**逐段校验和**模型记录（7/7 PASS 的证据更强）。

## 7. 0x214..0x378：type-6 扩展头（本任务重点，逐段解读）

### 7.1 `0x214..0x233`（跟在 checksum(R1) 之后）
`0x218=1`（未定）；`0x21C..0x230` 是 R4/R5 的 `(checksum, offset, size)` 两条描述（见 §2 表）。
→ `[确证]` 这一段属于**region 描述表**，不是独立扩展头；其字段顺序为
`[cksum(R4)][R4.off][R4.size][cksum(R5)][R5.off][R5.size]`（与 R0..R3 的 `[off][size][cksum]` 顺序不同，`[未定]` 为何不对称）。

### 7.2 `0x234..0x247` 填充
`FF FF FF FF / FF FF FF FF / 00000000 / FF FF FF FF / 00000000`
`[推测]` 是 region 描述表的「空槽/哨兵」，或与可选描述（最多若干条）相关的填充。

### 7.3 `0x248..0x273` R0..R3 描述
`[off R0][off R0 重复][size R0][off R1][size R1][off R2][size R2][cksum R2][off R3][size R3][cksum R3]`（§2 表已列）。

### 7.4 `0x274..0x2A7` 保留/图样/位打包区
- `0x274=0`，`0x278=0xFFFFFFFF`；
- `0x27C=0x55555555`，`0x280=0xAAAAAAAA` → **测试图样**（`[强]` 自检/对齐用）；
- `0x284..0x2A7`（9 个 u32）：
  `0xFFFFE51F, 0xFFFFFFE1, 0x000BEAFF, 0x1C0B1C0B, 0x000B7E7F, 0xFFFFFFFA, 0x008F0FC7, 0xFFFFFFFC, 0x000B7CCB`
  → `[推测]` 位打包/混合宽度表：既有负数样值（0xFFFFxxxx）、又有奇数（Thumb 地址 0xBEAFF/0xB7E7F/0xB7CCB）、又有重复字 `0x1C0B1C0B`。
  与 0x2A8 起的 8B 记录表相邻，可能是同一张表的「位打包段」。

### 7.5 `0x2A8..0x378` 8 字节记录表（26 条，**本任务重点**）
每条 `(u32 flag, u32 addr)`，LE：
```
#   file off    flag          addr          (addr&1)  addr as Thumb(addr&~1)
0   0x2A8  0xFFFFFFFE  0x0000AFADFF   1  0x0000AFADFE
1   0x2B0  0xFFFFFFFE  0x0000AFADFB   1  0x0000AFADFA  (-4)
...
23  0x360  0xFFFFFFFE  0x0000AFADA3   1  0x0000AFADA2  (-4)
24  0x368  0xFFFFFFFE  0x0000AFAC7B   1  0x0000AFAC7A  (-296)
25  0x370  0xFFFFFFFE  0x0000AFAC79   1  0x0000AFAC78  (-2)
```
统计：
- flag 只有两个值：`0xFFFFFFFE`（22 条）与 `0xFFFFFFFF`（4 条：第 6/7/9/10 条）。
- addr **全部为奇数** → 符合 **Thumb 函数指针**（Thumb 位=1）特征（`[强]`）。
- addr 区间 `0x00AFAC79..0x00AFADFF`（都在 0x00AF0000 段内，字符上像 32-bit 地址/偏移空间的一小段）。
- 25 个相邻步长中 23 个为 -4（指令对齐），在 0x368 处跳变 -296、0x370 处 -2 → 表在 0x368 附近「重新开始」一次（`[推测]` 两条子表/两组）。

解读候选（按证据强度）：
1. `[强]` **Thumb 指针/修正表（fixup/jump table）**：`addr` 是 0x00AFxxxx 段内的 Thumb 例程地址；`flag`（-2/-1）是类型/长度标记。
2. `[推测]` **补丁/覆写记录表**：flag=-2/-1 表示覆写长度或方向；文件名中的 `早期二改` 也可能暗示这是「AE fix」补丁相关表。
3. `[推测]` 若 header 实际到 0x378（§8），则它是扩展头的「尾部指针数组」，由相机/updater 在加载后修正这些地址。

未解：`0x00AFxxxx` 是「文件内偏移」还是「运行时内存地址」；flag 两个取值的具体含义；24 条 vs 26 条的分组。
