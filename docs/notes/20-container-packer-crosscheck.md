## 2. 四机型容器核验（codex 用实际字节建立）

### 2.1 origin 与字段位置

来源：`xt4-codex/analysis/container_research/结构与校验研究.md`、同目录四机 JSON 与 `summary.json`。

| 输入 | native DAT origin | 主范围 offset/length 字段 | 主校验字段 | 全部匹配项 |
|---|---:|---:|---:|---:|
| X-T4 | `0x274` | `0x244` / `0x248` | `0x20C` | 7/7 |
| X-H2S | `0x274` | `0x244` / `0x248` | `0x20C` | 6/6 |
| X-T5 | `0x274` | `0x244` / `0x248` | `0x20C` | 4/4 |
| X-M5 | `0x2BC` | `0x24C` / `0x250` | `0x214` | 4/4 |

* 四机合计 **21/21** 个声明范围的首尾连续、校验值与计算值完全一致。**【确证｜离线验证】**
* X-M5 的头更长（origin `0x2BC`），所以 **主校验字段不是固定的 `0x20C`**：公开 patcher 里"头长 = `codeSize+20`、从 `0x214` 开始取反"的假设对 X-M5 与 X-T4 都不成立。**【确证】**（与本仓库 §2.1 的 `0x274` 实测一致）
* 本仓库 §3.1 的字段表是 **X-T4 专用**（`0x248` 在本仓库被读成 `R0.offset`，在 codex 模型里它是"主范围长度"，数值同为 `0x2FC0020`，两读法数值不冲突、语义不同）。**不要把这张表直接套到新三机。**

### 2.2 计算式

```
主范围 / secondary1,2 / additional1,2 :  ~sum(raw_byte XOR 0xff) & 0xffffffff
restore1 / restore2                   :  ~sum(raw_byte) & 0xffffffff      # 不取反
```

* 即"先按范围取反、再求无符号字节和、最后按 32 位取反"。
* `restore1/2` 直接对**原始文件字节**求和 —— 与本仓库 §6.1 表中 R2/R3"只有按存储字节才命中"的结论一致，且这次是在**四个机型上同时成立**。**【确证｜离线验证】**
* 范围是"声明范围"：X-T4 的声明范围恰好覆盖到文件末尾；另三机在最后声明范围之后还有尾段（见 2.3）。

### 2.3 尾段：72 字节 DER 形状与"不证明无认证"

* X-H2S / X-T5 / X-M5 在最后声明范围后各剩 **72 字节**，形态严格符合 ASN.1 DER `SEQUENCE(INTEGER, INTEGER)`：两个 INTEGER 各 33 字节、首字节为零，各代表 256 位非负数。
* 该形状**高度符合常见椭圆曲线签名编码**，但 codex 明确记录：**没有公钥、没有验签、没有被签名消息范围证据**，因此 **不能断言算法**，更不能因为"普通校验和匹配"就认为绕过了认证。**【强（形状）/推测（算法）｜静态推断】**
* X-T4 **没有**同样的尾段。这同样只是一个阴性观察：**不能据此证明 X-T4 的所有代码路径都没有其它认证检查**。相机端是否验签、验什么，仍属未验证。

### 2.4 与本仓库单机结论的对齐

| 本仓库已有结论 | codex 四机核验 | 状态 |
|---|---|---|
| 头部 `0x274` 字节明文，其后 XOR 0xFF；校验和只在 `0x274` 起点命中 | X-T4/X-H2S/X-T5 origin 同为 `0x274` | 一致（X-M5 为 `0x2BC`，属另一布局） |
| 7 段首尾相接、无缝覆盖整个载荷；`~Σ` | 四机范围连续；21/21 匹配 | 一致，并扩展到四机型 |
| R2/R3 两段按"存储字节"求和（未取反） | `restore1/2` 在四机上都对原始字节求和 | 一致，例外规则被证实为通用规则 |
| 载荷按 `0x20000` 网格 | 描述符 `native_flash_offset` 均落在 `0x20000` 网格上（见 §3.2） | 一致，多一条独立印证 |
| 无整体签名/footer | 另三机有 72 B DER 形状尾段，X-T4 无 | 本仓库结论**不冲突**，但要补上 §2.3 的警示 |

## 3. 描述符表格式修正

### 3.1 X-T4 的表规格（codex 修正版）

| 项目 | 值 | 说明 |
|---|---:|---|
| 记录大小 | **36 B / 9 个 u32** | 不是 u16 表 |
| 表根（DAT 文件偏移） | **`0x140274`** | 即载荷偏移 `0x140000` |
| 候选运行地址 | **`0x00E20000`** | 由代码/头印证，属候选映射 |
| 首条记录 | 根 + `0x40` = `0x1402B4` | 根到首记录之间是表头/保留区 |
| 记录条数 | 9 条 | `id` = 0,1,2,9,3,4,5,6,7,8（JSON 顺序） |
| 终止项 | 根 + `0x1A8`（`0x14041C`），值为 **255** | codex JSON 的 `descriptor_terminator_value` |

* 字段候选语义（codex）：`id / load / image_size / bss_start / bss_size / native_flash_offset / flash_window / …`。
* 这些语义**只在有解压文件头/代码印证时才提升可信度**；对没有执行头的槽位（例如字体/资源），codex JSON 里的 `header_load_matches=false` **只表示"该头部不是执行映像头"**，不能解读为"整张表失效"。**【强｜静态推断】**

### 3.2 描述符 `native_flash_offset` ↔ 本仓库 §4 段表

把 codex `FWUP0024_XT4.json` 的描述符字段与 `FIRMWARE-STRUCTURE.md` §4 段表对照，可得到一条很干净的互证：**每个描述符的 flash offset 都等于对应段在载荷内的起点**（`0x20000` 网格）。

| id | native_flash_offset | 对应文件段起点（§4） | 段 |
|---:|---:|---:|---|
| 0 | `0x60000` | `0x60274` | 段 #2 引导/向量段 |
| 3 | `0x160000` | `0x160274` | 段 #6 代码/数据 A 副本 |
| 4 | `0x1E0000` | `0x1E0274` | 段 #8 代码/数据 B 副本 |
| 1 | `0x1A00000` | `0x1A00274` | 段 #13 FFLZ sec3（字体/资源） |
| 5 | `0x260000` | `0x260274` | 段 #10 FFLZ sec0 |
| 6 | `0x5C0000` | `0x5C0274` | 段 #11 FFLZ sec1 |
| 7 | `0xAE0000` | `0xAE0274` | 段 #12 FFLZ sec2 |
| 8 | `0x1820000` | `0x1820274` | 段 #14 未定性 |

另外两个值得注意的候选 load：槽 5 = `0x01021000`、槽 6 = `0x01E0F000`，与 codex `analysis/XT4研究进展.md`「输入与解包边界」给出的 `lz_00260274.bin` / `lz_005c0274.bin` 推定起点一致；这说明"描述符 load 字段"和"解压流映射"两条独立线索能对上（仍属**静态推断**，未用 RAM dump 验证）。

### 3.3 新三机的表：64 B / 8 个 u64（不是 72 B）

| 输入 | 表根 DAT | 候选根运行地址 | 首记录偏移 |
|---|---:|---:|---:|
| X-H2S | `0x1A0274` | `0x013E0000` | 根 + `0x50` |
| X-T5 | `0x1A0274` | `0x010C0000` | 根 + `0x50` |
| X-M5 | `0x6402BC` | `0x00040000` | 根 + `0x50` |

* **记录是 64 字节 / 8 个 64 位字**。若按 72 字节步长走，会读到错误字段；按 64 字节步长可读出完整连续 ID 并到达明确终止项。
* 第 6 个索引字的**低 32 位是 flash window 长度**，高 32 位常为 `0x40`，**用途尚未证明**。
* 同样：字段含义要等"对应解压文件头/代码印证"才可提升可信度；**不能把 X-T4 的字段解释外推到新三机**。

### 3.4 与本仓库 §4 段表 #5 旧描述的对照（本次修正）

本仓库 `FIRMWARE-STRUCTURE.md` §4 段表第 5 行原先把 `0x140274` 写成"**小表 `0x241`：u16 递增表，其余 `0x00` 填充**"。codex 在同一偏移识别出 36 B/9×u32 的描述符表（首记录根 +0x40）。

* **结论**：`0x140274` 应按"**描述符表根**"理解；"小表/u16 递增表"是旧笔记里较粗的读数，**不应再作为该区段的定性**。**【强｜静态推断】**（两个项目的读数不同，codex 的版本能同时解释记录步长、终止项和 flash offset 网格）
* **保留余地**：本次没有重新读该区段字节，"旧读数为何会出现 u16 递增形态"未复核；若后续有人复算，请注意确认基准文件身份（§1）——`aefix_1106` 与官方在此区段是否逐字节相同，旧笔记没有单独记录。
* 该修正已同步写入 [FIRMWARE-STRUCTURE.md](../FIRMWARE-STRUCTURE.md) §4 与新增 §14。

### 3.5 字段语义的边界

* 只有部分槽位有"解压文件头再次包含相同 load/image size 及正文内入口"的印证（X-T4 槽 5/6 等）；其余字段是**候选语义**。
* 描述符里的 `flash_window` 与槽容量、`0x20000` 段起点、压缩记录长度的关系**尚未全部证明**；不要用描述符字段去反推压缩格式细节。

## 4. LZ 页边界：19 条流逐 token 复算

### 4.1 结果

来源：`xt4-codex/analysis/container_research/结构与校验研究.md`「LZ页边界」，逐机计数在各自 JSON 的 `LZ_token_shapes`。

* 对四机**全部 19 条 LZ 流**再次逐 token 遍历：输出长度全部与头部字段一致；**没有 token 跨越 `0x4000` 字节记录页边界**；**所有内部页边界都有 token 恰好结束**。**【确证｜离线验证】**
* X-T4 四条流的计数（同一 JSON 记录，可与本仓库 §7.3 的 pages 对照）：

| 流（DAT 起点） | 页数 | 内部页边界 | token 总数 | literal / match | 距离范围 | 最大长度 |
|---|---:|---:|---:|---:|---:|---:|
| `0x260274`（sec0） | 211 | 210 | 1,326,123 | 476,849 / 849,274 | 3..2047 | 15 |
| `0x5C0274`（sec1） | 321 | 320 | 2,017,942 | 791,222 / 1,226,720 | 3..2047 | 15 |
| `0xAE0274`（sec2） | 283 | 282 | 1,694,264 | 608,374 / 1,085,890 | 3..2047 | 15 |
| `0x1A00274`（sec3） | 203 | 202 | 1,202,361 | 372,734 / 829,627 | 3..2047 | 15 |

* 同一 JSON 还记录：`crossing_token_examples` / `overlapping_match_examples` / `zero_token_examples` 均为空 —— 即**实际数据里没有跨页 token、没有自重叠回溯**。**【离线验证】**（阴性结果仅覆盖已解码的这 19 条流）

### 4.2 与本仓库 §7.2 的关系

本仓库 §7.2 的结论是："token 流必须**整体连续**解码，不能按 16 KiB 页切开逐页解；硬件逐页喂 16 KiB **压缩**数据，编码器保证**没有 token 跨页**，但**字面量的字节数据可以跨页**。"

codex 的逐 token 复算把这句话从"经验/踩坑"升级为**可计量的事实**：对已结构解码的全部流，每个内部 `0x4000` 边界都恰好是某个 token 的结束位置。两者的表述可以合并为：

1. **解码**：整体连续，不按页切。**【确证】**
2. **编码**：token 边界必须与 feed 页边界对齐——任何 token（字面量 run 或回溯）都不得跨页。**【确证｜离线验证】** 对"硬件为什么这样要求"的唯一解释仍是 inference（硬件逐页解压），属**【推测｜静态推断】**。

> 推论：一次"只改内容、不重压缩"的补丁不受这条约束影响；一旦重编码，**页边界与无自重叠就是硬门槛**。见 §5。

## 5. codex 的离线 packer：结论与门槛

来源：`xt4-codex/tools/packer_research/README.md`、`xt4-codex/analysis/packer_research/validation.json`（前 100 行 + 尾部门禁清单）、`xt4-codex/tools/packer_research/fflz_encode.c`（说明）。

### 5.1 编码器规格（实际输出遵守的规则）

| 维度 | 规则 | 性质 |
|---|---|---|
| 滑动窗口 | 2047 字节 | 与解码距离上限一致 |
| 匹配策略 | 贪心最长匹配 | 与原始流的匹配选择一致（逐字节回环证明） |
| 长度上限 | 15 | 与 `len = b & 0x0F` 一致 |
| 等长选择 | 取**最近距离** | 由逐字节回环反推 |
| 自重叠 | **无**（`len ≤ distance`） | 由逐字节回环 + 统计空集反推 |
| 页边界 | 实际输出遵守 `0x4000` feed 页边界 | 由原始流反推 + 校验器强制 |
| 匹配域 | 距离 3..2047、长度 1..15 且 `len ≤ distance`；长度 1/2 只允许紧邻 feed 边界 | 观察到的匹配域，未见其它形态 |

* 编码器另有严格独立解码器、输入身份门禁、同长度槽位替换、7 个范围校验重算、磁盘副本重新提取、非允许字节全量比较。

### 5.2 四个原始槽位的逐字节回环（**官方 v2.12 基准**）

| 槽位 | 解压字节 | 编码字节 | 原 flash 容量 | 容量剩余 | 编码/原图 |
|---|---:|---:|---:|---:|---:|
| 5（sec0） | 7,420,408 | 3,449,330 | 3,538,944 | 89,614 | 46.48% |
| 6（sec1） | 9,437,184 | 5,254,523 | 5,373,952 | 119,429 | 55.68% |
| 7（sec2） | 10,240,000 | 4,632,713 | 4,718,592 | 85,879 | 45.24% |
| font1（sec3） | 6,446,348 | 3,309,617 | 3,407,872 | 98,255 | 51.34% |

* 四个原始流不只是"解压等价"：**重新编码得到与原始记录逐字节相同的压缩记录，放回后整份 DAT 也逐字节相同**（`record_byte_identical=true`、`container_byte_identical=true`，容器 SHA 回到 `853d273b…`）。**【确证｜离线验证】**
* 这一步同时检验了匹配选择、literal 分组、页边界处理三条规则——能把原始流逐字节复现，说明规则集至少对这四个槽位的原始数据是完备的。
* **注意基准**：上表数字全部基于**官方 v2.12**（`853d273b`）。`aefix_1106`（`618a3edd`）的 sec0 packed 是 3,449,482（本仓库 §1.1），当前工作副本 `dfc98269` 又不同。**不要把容量余量直接套到你的工作副本上。**

### 5.3 合成标记测试与门禁

* **合成单字节标记**：只把槽位 5 解压数据的最后一个字节（解压偏移 `0x7139F7`）由 `0x00` 改成 `0xA5`，重新编码/装回后：严格解压准确恢复该修改、七个范围校验全部匹配、其余槽位及非允许字节不变、保存后从磁盘重新读取仍一致。产物是 `synthetic_marker_slot5.not-for-camera.bin`（容器 SHA `4d84fd18…`），**不是功能固件**。**【确证｜离线验证】**
* **十项拒绝测试**（`validation.json` 的 `negative_gates`，逐项 `refused=true`）：
  1. 非 X-T4 2.12 源（X-M5）拒绝；
  2. 被改过的 X-T4 源拒绝；
  3. 解压尺寸变化拒绝；
  4. 执行头/前缀变化拒绝；
  5. flash 分配变小拒绝（编码器报超出原容量）；
  6. 产物写到工作区根目录拒绝（强制留在研究目录）；
  7. 槽位/校验字段之外的字节变化拒绝；
  8. feed 页数不符拒绝；
  9. 零控制 token 拒绝；
  10. 跨页 token（literal 跨页）拒绝。
* **门禁仍关闭**：`deployment_gate = CLOSED: no hardware decode/updater-authentication proof`。合成产物明确标注 `NOT FOR CAMERA`，也不含 F-Log2 功能。

### 5.4 与本仓库"重编码教训"的联系

据项目记录（2026-11-11，见 [CROSS-REF-CODEX.md](../CROSS-REF-CODEX.md) §2 的对照表；公开笔记未保留该失败包的逐条记录，相邻背景见 [15-patch-no-reala-rightcol.md](15-patch-no-reala-rightcol.md) §7.2–7.3 关于 copy 共享导致连带改坏、v3/v4 在验证阶段被拒绝交付的过程），本仓库曾用**未加约束的贪心重编码**生成测试固件，产物出现**自重叠 copy**，刷入后相机无响应。**【项目记录 / 待补证据】**

codex 的约束集正好补上这一课：

* **无自重叠**（`len ≤ distance`）：解码器允许重叠复制（§7.2 原文"允许重叠"），但**原始编码器显然不用**；用重叠 copy 的编码器产出的流"能解压、长度对、校验过"，却可能不被硬件解压器接受或触发未验证行为。**能解压 ≠ 相机接受。**
* **页边界**：把 token 对齐到 `0x4000` feed 页，是原始流 19/19 条都满足的硬约束；不满足的流可能只在硬件上失败，离线解码器发现不了。
* **逐字节回环**：把"重新编码结果 == 原始记录"当作回归门槛，能一次性排除匹配策略、literal 分组、页边界的偏差。
* **7/7 校验 + 磁盘回读**：把"写入路径"也纳入验证，而不是只在内存里比对。

### 5.5 `tools/fflz_rebuild.py` 应如何对照（只给方向，不改代码）

本仓库 [fflz_rebuild.py](../../tools/fflz_rebuild.py) 是"能跑通"的重打包脚本，但**不是受约束的编码器**。按文件头注释与实现阅读（**代码阅读，未运行**）：

| 维度 | codex 编码器 | 本仓库 `fflz_rebuild.py`（阅读结论） | 建议方向 |
|---|---|---|---|
| 输入身份 | 固定 `853d273b` | 直接读 `FWUP0024.DAT`，不校验 SHA | 入口处加 SHA 白名单 |
| 距离域 | 3..2047 | 允许 1..2047（只排除 0） | 收紧到 3..2047 |
| 自重叠 | 禁止（`len ≤ distance`） | 未检查 `len ≤ distance` | 编码/校验两侧都拒绝 |
| 页边界 | 强制 token 不跨 `0x4000` | 未实现页边界逻辑 | 按 feed 页分组编码，或直接复用受约束实现 |
| 长度 0x4000 倍数 | 拒绝 | 未检查 | 加门禁 |
| 解码长度一致性 | 严格 | `decode_stream` 明确**不校验**解压长度（注释：sec3 曾多 21 B） | 校验或至少报警 |
| 校验覆盖 | 7 个范围全重算 | 只重算主校验 `0x20C` | 加 R0..R5 复算（可复用 `tools/hdr.py`） |
| 回归门槛 | 逐字节回环 + 磁盘回读 | 无 | 增加"等价重压缩 == 原记录"自检 |

> 方向性结论：**不要**把 `fflz_rebuild.py` 的编码输出直接当作可刷候选；它的价值在"快速验证内容改动"，不在"产出符合原始编码器约束的流"。真正的逐字节一致性门槛以 codex 的验证方法为准（方法可借鉴，产物不可引用）。

## 6. 给 xt4 读者的可操作结论

1. **优先"只改字面量字节、不重压缩"**：用 [fflz_trace.py](../../tools/fflz_trace.py) 判断目标字节是 literal 还是 copy；literal 可原地改，copy 必须改源头。这是本仓库 15 号补丁（实机通过）的路线，风险最低。
2. **必须重编码时**，按 §5.1 的约束集写编码器：窗口 2047、贪心最长匹配、len≤15、等长取最近距离、**len ≤ distance（无自重叠）**、**token 不跨 `0x4000` 页**、距离 3..2047、长度 1/2 仅限 feed 边界。
3. **页边界的两种含义都要满足**：解码时整体连续（不按页切）；编码时 token 按页对齐。只满足前者会在硬件上暴露问题。
4. **回归门槛用"逐字节回环"**：先做"原内容重新编码 == 原始记录"的 S1 验证（本仓库 15 号 §7.3 的 S1 思路），再改内容；改完做 7/7 校验 + 磁盘回读 + 独立解压。
5. **每次产出都记录基准 SHA**：源文件、产物、以及"相对哪一份"的偏移。工作区三份变体的偏移结论不可混用（§1）。
6. **不要把"校验和通过"当成"相机接受"**：更新器认证、硬件解压器行为、恢复路径都未验证；DFU 失败可能没有软件回退。
7. **配额意识**：四个槽位的容量余量在官方基准上是 85–119 KB 量级（§5.2）；内容增长要留余量，且不得移动槽位/改变解压尺寸（codex 门禁明确拒绝）。

## 7. 未解与风险

| # | 问题 | 现状 |
|---|---|---|
| 1 | X-T4 是否存在其它认证/验签 | 无 DER 尾段**不证明**没有；相机端行为未观测 |
| 2 | 硬件解压器是否接受"合规但非原样"的流 | codex 只验证了离线解码；硬件行为未验证 |
| 3 | 更新器是否接受修改包 | codex 部署门禁关闭；本仓库实测候选只证明"能刷"，不证明"任意重编码都能刷" |
| 4 | 描述符字段语义 | 部分靠文件头/代码印证，其余候选；新三机字段含义更不能外推 |
| 5 | 四机型尾段 72 B 的算法 | 形状像 ECDSA，但无公钥/验签证据，**不能断言** |
| 6 | `0x140274` 旧"u16 递增表"读数的来源 | 未复核；修正为描述符表属【强】而非【确证】 |
| 7 | packer 数字的基准 | 全部基于官方 `853d273b`；当前工作副本 `dfc98269` 需另行取得容量/余量 |
| 8 | codex 快照时效 | 2026-11-12 文本快照，状态类结论以各包最新状态文件为准 |
