## 2. 总体结构

```
文件偏移（大小）：
0x000000 (0x274 = 628 B)  ┌─────────────────────────────────────────────┐
                          │ L1：明文容器头                               │
                          │  0x000 u32 os_type = 6                       │
                          │  0x004..0x203 model code (512 B, 双层 hex)   │
                          │  0x204 version1 = 2                          │
                          │  0x208 version2 = 0x12  → 显示 v2.12         │
                          │  0x20C 主校验和 = 0x56B4BFF5                 │
                          │  0x210..0x273 6 个 region 的 (cksum,off,size)│
                          └─────────────────────────────────────────────┘
0x000274 (51,277,652 B)   ┌─────────────────────────────────────────────┐
                          │ L2：固件载荷，逐字节 XOR 0xFF                │
                          │  · 段数据起点 = 载荷偏移 0x20000*k           │
                          │    = 文件 0x274 + 0x20000*k                  │
                          │  · 明文段(引导/ThreadX 内核/机型描述/…)      │
                          │  · 4 个 FFLZ 压缩段                          │
                          │  · 尾部 6 个 region（R0..R5，1.21 MB）       │
                          │  · 大段 0xFF（擦除）                         │
0x30E71C8                 └─────────────────────────────────────────────┘
```

### 2.1 编码层：XOR 0xFF，起点 `0x274`

**判定证据**（全部可复算）

1. `FUJIFILM` 原样 **0** 次、取反后 **10** 次；`Copyright`、`syslog`、`http://`、`ThreadX`、`X-T4` 同样只在取反域出现。
2. 取反后 `0x000A78` 起是规整 **Thumb-2**：`F10E 01D3`(`ADD.W`)、`EB00000C`(`BL`)、`E3500000`(`CMP`)、`1E FF 2E E1`(`BX LR`)。
3. 取反后 `0x020274` 起是标准 **ARM 异常向量表**：8×`18 F0 9F E5`(`LDR pc,[pc,#24]`)，随后 `FE FF FF EA`(`B .`)，capstone 覆盖率 **100%**。
4. 取反后直接读到 `Copyright (c) 1996-2015 Express Logic Inc. * ThreadX SMP/Cortex-A7/GNU Version G5.6.2.5.0 SN: 3874-271-0519`（`file 0x7B250`）。
5. **校验和只在 `0x274` 起点时命中**（见 §6）——这是确定起点最硬的证据。
6. region 偏移链末端 `0x30CEF54 + 0x18000 = 0x30E6F54 = filesize − 0x274`（精确）。

**逻辑镜像**：`logical = file[0:0x274] + ~file[0x274:]`（`tools/decode2.py` → `out/decoded.bin`）。

> 与公开实现的差异：`fujihack/patcher` 等把 payload 起点定在 `FujiFirmHeader` 长度 `codeSize+20 = 0x214`，从 `0x214` 开始取反。实测真正的物理起点是 **`0x274`**（多出的 `0x214..0x273` 是 region 描述表，本身也是明文）。两种取法只差这 0x60 字节，做代码/资源分析无影响，但**校验和验证必须以 0x274 为基准**。

### 2.2 载荷层：0x20000 网格

```
段数据起点（载荷内偏移）= 0x20000 * k        (k = 0,1,2,…)
对应文件偏移            = 0x274 + 0x20000 * k
```

已核实落在该余数上的起点（文件偏移）：`0x0020274, 0x0060274, 0x00C0274, 0x0140274, 0x0160274, 0x0180274, 0x01E0274, 0x0200274, 0x0260274, 0x05C0274, 0x0AE0274, 0x1820274, 0x1860274, 0x1A00274, 0x1DA0274, 0x2FC0274`。

* **每块前 0x274 字节恰好就是文件头的长度**——这不是「块头」，而是**载荷整体前移了 0x274**：载荷内所有段都按 128 KiB 对齐。即 `0x274` 不是每块重复的前缀，而是「文件头长度 = 载荷对齐偏移」。
* 公开资料对该网格无记载（只有「FFLZ 按 16 KiB 页解压」「老 FinePix 用 512 字节块单位」等间接事实）。

### 3.2 model-code 区（`0x004..0x203`）

512 字节形如 `33 30 33 30 33 30 33 35 …`，是「**ASCII-hex 的 ASCII-hex**」：
第 1 次 hex 解码 → 256 字节仍是数字文本；第 2 次解码 → 128 字节 = **32 × u32 BE**，其中 **11 个非空槽**：

```
slot00..03: 0x00056001 0x00056002 0x00056004 0x00056009
slot04..10: 0x00057001 0x00057002 0x00057004 0x00057005 0x00057006 0x00057007 0x00057008
slot11..31: 0x00000000
```

* 官方 v2.12 与本文件此区**逐字节相同** ⇒ 固定字段，与 `早期二改` 改动无关。
* 语义未定论：①「本包包含哪些子更新/目标器件」清单；②`前 6 位 base + 后 2 位 区域/变体`；③内部器件 ID 表。【存疑】

## 5. 载荷起始处的 26 条记录表（`file 0x2A8..0x377`，载荷偏移 `0x34..0x103`）

26 条 × 8 字节，`(u32 flag, u32 addr)`。

**先定方向**：§6 的校验和已证明 `payload[0 .. 0x2FC0020)` 在文件里是**取反**存储（`0xFFFFFFFF − Σ(logical bytes)` 精确命中），所以 `0x274` 之后的**逻辑域**才是真实内容 ⇒ 本表应以逻辑域读为准：

* **逻辑（真实）读法**：`flag ∈ {1（22 条）, 0（4 条）}`，`addr = 0xFF505200, 0xFF505204, 0xFF505208, …`（连续 **升序 +4**，共 24 个），末两条跳到 `0xFF505384 / 0xFF505386`。
* 相邻的 `0x284..0x2A7`（9 个 u32）在逻辑域为：`0xFFFFE51F→0x00001AE0`、`0xFFFFFFE1→0x0000001E`、`0x000BEAFF→0xFFF41500`、`0x1C0B1C0B→0xE3F4E3F4`、`0x000B7E7F→0xFFF48180`、`0xFFFFFFFA→0x00000005`、`0x008F0FC7→0xFF70F038`、`0xFFFFFFFC→0x00000003`、`0x000B7CCB→0xFFF48334`。
* 逻辑域里集中出现 `0xFF50_52xx` 与 `0xFFF4_xxxx` 这类**高端地址**，更像「**启动/向量/寄存器地址表**」；而按存储域读出的 `0x00AFAC79..0x00AFADFF`（递减、全奇数、像 Thumb 指针）恰好是取反造成的镜像形态 —— 且 `0x00AFAxxx` 若解释成载荷偏移会落在压缩流内部，不合理。

⇒ 结论：**这是一张指向高端地址空间（`0xFF50xxxx` / `0xFFF4xxxx`）的 `(有效标志, 地址)` 表**，疑似启动向量/MMIO 初始化表；具体目标未验证。【强（读法）/ 推测（用途）】

同一区域还有：
* `0x27C/0x280`：`0x55555555 / 0xAAAAAAAA`（逻辑域 `0xAAAAAAAA / 0x55555555`）→ 测试图样，与公开资料记录的 `aa 55 00 ff` 同族【强】

## 6. 校验和：`0xFFFFFFFF − Σ(bytes)`（7 段无缝覆盖整个载荷）

### 6.1 算法

```
checksum(span) = (0xFFFFFFFF − (Σ span_bytes)) & 0xFFFFFFFF      # 8-bit 字节和取反
```

* 主校验和 `@0x20C` 覆盖 **main body = 逻辑载荷 `[0x000000, 0x2FC0020)`**。
* 其余 6 个 `@0x210/0x214/0x21C/0x228/0x264/0x270` 分别覆盖 **R0..R5**。
* **7 段首尾相接、无缝覆盖整个载荷**（51,277,652 B）：这同时解释了 `u32@0x000 = 6` = region 描述条数。

**独立复算结果（Lead 已用 Python 复现）**

|---|---|---|---|---|---|---|
| main body | `0x000000` | 50,069,536 | `0x56B4BFF5`@0x20C | `0x56B4BFF5` | `0xB0472029` | ✅ 逻辑 |
| R0 | `0x02FC0020` | 49,152 | `0xFF6DB51F`@0x210 | `0xFF6DB51F` | `0xFFD30ADF` | ✅ 逻辑 |
| R1 | `0x02FCC020` | 863,484 | `0xF657A35A`@0x214 | `0xF657A35A` | `0xFC888DA0` | ✅ 逻辑 |
| R2 | `0x0309ED1C` | 368 | `0xFFFFB7D8`@0x264 | `0xFFFED996` | `0xFFFFB7D8` | ✅ **存储** |

* **R2/R3 是唯一两个「按存储字节」才命中的段** ⇒ 这两段很可能**未被取反**（在文件里是明文）。实测其内容确实是规则的索引表：
  * **R2** = 一串 `(u16 offset, u16 length)`（升序），`file 0x309EF90`，例：`(0x0080,0xA2) (0xA2,0x01) (0xA8,0x01) (0xC4,0x01) (0xF2,0x01) (0x102,0x04) (0x11B,0x1E) …`

  ⇒ 两者都是「**区间/跨度索引表**」形态，疑为更新器的写入映射或记录索引。【强】
* 公开资料里「checksum = 字节和」的说法**不完整**（缺了取反 + 分段）；prior-art 得到的经验式 `Σ(raw[0x214..EOF]) + 0x02FD03C5` 只是本分段公式的代数变形（常量项由「头 0x214..0x273 与尾段字节不变」导致），**分段公式才是真的**。【确证】

## 7. FFLZ 压缩格式（已完整复现）

### 7.1 段头（20 字节，小端；位于文件 `0x274 + 0x20000*k`，处于**逻辑**域）

| 偏移 | 类型 | 字段 | 本文件 |
|---|---|---|---|
| `+0` | u32 | `unpacked_size` | 解压后长度 |
| `+4` | u32 | `packed_size` | 压缩流长度 |
| `+8` | u32 | `pages` | `= ceil(packed_size / page_size)` |
| `+12` | u32 | `page_size` | `0x4000`（16 KiB） |
| `+16` | u32 | `tag` | `4`（X-T4） |
| `+20` | — | token 流 | |

### 7.2 token 规则（LZ77 变体，文献近似 Fiala–Greene "Algorithm A1"）

```
token < 0x80 : 字面量。token 值 = N，紧随 N 个原始字节。
token >= 0x80: 双字节回溯。读下一字节 B：
                 length   = B & 0x0F
                 distance = ((token & 0x7F) << 4) | (B >> 4)      # 1..2047
                 从输出尾部回退 distance 字节复制 length 字节（允许重叠）。
```

**关键实现细节（踩过的坑）**：token 流必须**整体连续**解码，**不能**按 16 KiB 页切开逐页解。
硬件是逐页喂 16 KiB **压缩**数据，编码器保证**没有 token 跨页**；但**字面量的字节数据可以跨页**。按页切断会每页丢掉字面量溢出的部分（第一段会少 **10,482** 字节，正是此陷阱）。连续解码后 4 段长度**精确匹配**。

## 13. 结论

1. 这个 `.DAT` 是**两层结构**：628 字节明文容器头（os_type / model-code / 版本 / 7 个校验和描述）+ **51.28 MB 逐字节取反的固件载荷**。
2. 载荷是**按 128 KiB 网格对齐的分段布局**（段正文 = 载荷偏移 `0x20000*k`）：少量明文段（引导、ThreadX 内核、机型/硬件描述、若干代码副本）+ **4 个 FFLZ 压缩段**（解压后 33.5 MB）+ 尾部 6 个独立校验的 region（1.21 MB）。
3. **完整性机制已完全解出**：`0xFFFFFFFF − Σ(bytes)`，7 段无缝覆盖整个载荷，7/7 复算通过；其中 R2/R3 两段是**未取反的明文索引表**。
4. 用「取反（base 0x274）+ FFLZ 连续 token 解码」这条链路，**已可完整还原 33.5 MB 主体**（长度逐个精确校验），解压段里能看到完整 ThreadX、UI 资源、网络栈、Exif/XMP 模板——**已具备继续做代码级逆向的基础**。
5. 本文件是**官方 X-T4 v2.12 的二次构建**（`早期二改`）：头/段布局/解压长度全同，改动集中在 sec0/sec1/sec3 三段压缩流与主校验和，**sec2 完全未动**；但**解压后真实内容改动只有约 55.6 KB**（sec0 44,151 / sec1 3,517 / sec3 7,967 B），另外在尾部目录区**多写了约 17.7 KB 的 UTF-16LE 多语言界面文本**（官方为 `0xFF`）。模型串 `X-T4 → X-M5`（`file 0xC03D0`，2 字节）是另一处确定性差异，含义未定论。
